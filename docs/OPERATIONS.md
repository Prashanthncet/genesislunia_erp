# Operations — deploy, backup, recovery, monitoring

Authoritative for the current stack (Next.js + NestJS + Prisma, SQLite **or** PostgreSQL). Older files in
`docs/` describe the retired Hono/D1/Cloudflare setup.

## 1. Choose the database
| | SQLite (default) | PostgreSQL (plan's production DB) |
|---|---|---|
| Use for | one server, a pilot or a couple of small schools | several schools, more than one API server, AWS RDS |
| Build | `docker compose build` | `docker build --build-arg DB_PROVIDER=postgresql ./backend` |
| Schema | `prisma/schema.prisma` | `prisma/postgres/schema.prisma` (generated by `scripts/make-postgres-schema.js` — never edit by hand) |
| Migrations | `prisma/migrations` | `prisma/postgres/migrations` |
| Backups | `VACUUM INTO` snapshot | `pg_dump -Fc` (+ `pg_restore --list` check) |

**PostgreSQL databases must be UTF-8** (`CREATE DATABASE erp WITH ENCODING 'UTF8' TEMPLATE template0`).
A cluster initialised with a Windows code page (WIN1252) cannot store "₹", "→" or Devanagari names.
Managed services (RDS, Cloud SQL, Neon, Supabase) are UTF-8 by default.

Both are verified: the full e2e suite (366 tests) passes on SQLite and on PostgreSQL 17
(`E2E_PG_ADMIN_URL=… npm run test:e2e:pg`; CI runs both).

SQLite is tuned automatically (`prisma/prisma.service.ts`): WAL journal, one connection
(`SQLITE_CONNECTIONS`, default 1), 30 s busy timeout, and transactions queued in-process. Without this, a burst
of concurrent writes deadlocked SQLite's single writer (measured: 72% of writes failed). SQLite therefore
means **one API process** — scale out only on PostgreSQL.

## 2. Deploy (single server, Docker Compose)
```bash
JWT_SECRET=$(openssl rand -hex 48) PUBLIC_URL=https://erp.school.edu docker compose up -d --build
```
Containers: `api` (migrations applied on start), `web` (Next.js on 5173), `backup` (daily). Put HTTPS
(nginx / Caddy / a load balancer) in front of `web`. Optional `redis` service is commented in the file.

Required in production (`NODE_ENV=production` refuses to boot without the first two):

| Variable | Why |
|---|---|
| `JWT_SECRET` | signs every login token |
| `CORS_ORIGINS` | allowed browser origins |
| `FRONTEND_URL` | absolute links in parent messages |
| `TRUST_PROXY=1` | behind a proxy; otherwise every user shares one rate-limit bucket |
| `STORAGE_DRIVER=s3` + `S3_*` | documents in S3 / Cloudflare R2 (local disk needs `STORAGE_ALLOW_LOCAL=1`, single server only) |
| SMTP_* / MSG91_* / TWILIO_* (or `NOTIFY_WEBHOOK_URL` + `_SECRET`) | real email/SMS/WhatsApp (unset channel = logged as `mocked`) |
| `RAZORPAY_KEY_ID` / `_KEY_SECRET` / `_WEBHOOK_SECRET` | online fees (unset = mock gateway, refused in production) |
| `TZ_SCHOOL` | the school's timezone for times typed without a zone (default `Asia/Kolkata`) |

Optional: `REDIS_URL` (shared report cache + rate limits across API instances), `SENTRY_DSN`,
`ALERT_WEBHOOK_URL`, `SWAGGER_ENABLED=1`. Full list with comments: `backend/.env.example`.

The Next.js `BACKEND_URL` is baked in at **build** time (rewrites are evaluated then) — it is a build arg.

Adding a school = insert a `branches` row (unique `code`) and create its admin with `POST /api/auth/users` as
a super admin. Never run `prisma db seed` against production: it wipes the demo branches (it refuses under
`NODE_ENV=production` unless `SEED_ALLOW_PRODUCTION=1`).

Moving legacy in-database documents into storage (once, after upgrading):
`node scripts/migrate-documents-to-storage.js --dry-run`, then without `--dry-run`. Idempotent.

## 3. Backup & disaster recovery
- `npm run backup` (`backend/scripts/backup-db.js`), run daily by the compose `backup` service:
  - SQLite: online `VACUUM INTO` snapshot + `PRAGMA integrity_check` on the copy.
  - PostgreSQL: `pg_dump -Fc` + `pg_restore --list` (archive readable, students data present). Needs
    `pg_dump` of the server's major version (`PG_DUMP_BIN` / `PG_RESTORE_BIN` to override; the Postgres image
    installs client 17 from the PostgreSQL apt repository).
  - Keeps `BACKUP_KEEP` (14) local copies; with `BACKUP_S3_BUCKET` + `S3_*` also uploads each one off-site,
    confirms it by a size-checked HEAD, keeps `BACKUP_KEEP_REMOTE` (30). Non-zero exit on any failure.
- Restore:
  - SQLite: stop `api`, copy an `erp-*.db` over the database file, start `api`.
  - PostgreSQL: `pg_restore --clean --if-exists --no-owner -d <database-url> erp-<stamp>.dump`.
  - Restore drill done 2026-10-22: dump → empty database → row counts identical on 11 core tables.
- Documents: with `STORAGE_DRIVER=s3` they live in the bucket (enable bucket versioning). With the local
  driver they are only on the server's disk — `backup-db.js` does not copy them.
- Targets with daily backups: RPO ≤ 24 h, RTO ≈ 15 min. Drill a restore every term.

## 4. Monitoring & alerting
- `GET /api/health` → `{status, db, db_ms, redis?, uptime_s, version}`; 503 when the DB (or a configured
  Redis) is down. Docker `HEALTHCHECK` uses it. Point an uptime monitor at it.
- One log line per request with a request id (`X-Request-Id`): JSON in production; 5xx → `error`,
  >1 s → `warn`.
- 5xx errors → Sentry when `SENTRY_DSN` is set (auth headers, cookies, bodies and query strings stripped) and
  a JSON POST to `ALERT_WEBHOOK_URL` (deduplicated per error for 5 minutes). Browser errors are reported to
  `POST /api/telemetry/client-error`.
- Failed messages: `notification_logs.status='failed'` with `last_error`; non-secret ones are retried at
  1 m / 5 m / 30 m / 2 h (max 5 attempts) by a job that runs once per minute across all instances (`job_runs`
  lock). Messages containing passwords/OTPs are never retried (they are stored masked).

## 5. Load testing
```bash
cd backend && LOGIN_RATE_LIMIT=1000 GLOBAL_RATE_LIMIT=1000000 npm run start:prod   # throwaway database only
npm run load-test -- --url http://localhost:3001 --concurrency 30 --seconds 30 --writes 0.25
```
Logs in staff and parents of both seeded schools, mixes reads with `--writes` share of real writes
(attendance + fee invoice/payment), reports p50/p95/p99, and fails on any cross-school id in a response.

Measured 2026-10-22 on a laptop with ~1.5 GB free RAM (expect better on a real server):

| Run | Requests / 30 s | Errors | p50 | p95 | Leaks |
|---|---|---|---|---|---|
| SQLite, reads only, 40 clients | 5,564 | 0 | 202 ms | 427 ms | 0 |
| SQLite, 25% writes, 30 clients | 991 (325 writes) | 0 | 332 ms | 1.8 s | 0 |
| PostgreSQL, 25% writes, 30 clients | 1,130 (391 writes) | 0 | 338 ms | 1.0 s | 0 |
| PostgreSQL, reads only, 40 clients | 2,772 | 0 | 409 ms | 820 ms | 0 |

## 6. Scaling path (plan §2.6)
1. PostgreSQL (RDS) + `STORAGE_DRIVER=s3` (S3 or R2) + `REDIS_URL` (ElastiCache) → run several API
   containers behind a load balancer. Scheduled jobs already run once across instances (`job_runs` lock).
2. Moving from R2 to AWS S3 is configuration only (`S3_ENDPOINT`, credentials, bucket).
