1. Objective of This Document

This document defines the technology stack for the School ERP system, explains why each choice was made over
comparable alternatives, sequences all 14 modules into delivery phases, and assigns concrete, phase-by-phase
deliverables to each of the two engineers on the team. It is meant to be the single reference both engineers and the
reviewer (you) use to track who owns what, and when.

  Team assumption
  Two engineers: one owns the entire frontend (React application, all screens, all roles), one owns the entire
  backend (API, database, integrations, jobs, deployment). Adjust names/assignments below as needed --
  the task breakdown stays the same regardless of who is assigned to which side.

2. Framework Decision & Rationale

The workflow you provided (Sections 1­9 of the Admissions flow) is not a simple form-and-database app. It has
6+ distinct roles, ~9 sequential approval states with branching (Valid/Invalid, Approve/Reject), scheduled
reminders, external payment and messaging integrations, and document handling. The stack below is chosen
specifically to handle that complexity cleanly, not just to get an MVP out fast.

2.1 Frontend -- React (fixed)

React was specified as the required framework. Within React, the following supporting choices are made to fit
this specific problem:

 · Vite + TypeScript -- faster dev/build cycle than CRA (which is deprecated); TypeScript is not optional here
    because the app has ~10 status values and 6+ roles -- a typo in a status string becomes a silent workflow bug,
    not a compile error, unless it's typed.

 · React Hook Form + Zod -- the Admission Form's fields are dynamic (AO can add/delete mandatory fields
    per academic year), so the form and its validation schema both need to be data-driven rather than hardcoded.

 · TanStack Query -- every dashboard in this system (AO, Accounts, OS, VP, Principal) is really the same
    pattern: fetch a filtered list, mutate a status, refetch. TanStack Query handles caching, refetching, and
    loading/error states for that pattern without hand-rolled state management.

 · shadcn/ui + Tailwind CSS -- pre-built accessible components (tables, dialogs, forms) that are fully
    customizable, so 6 role-based dashboards can be built quickly without a heavy design system.

 · React Router -- role-based route protection (a Parent should never reach the Principal's approval queue, etc.).

 · Zustand (lightweight) -- only for auth/session/role context; avoids the boilerplate of Redux for a 2-person
    team.

2.3 Database -- PostgreSQL

The data model is fundamentally relational: Student  Parent  Documents  Fee Payment  Roll Number 
House, all linked by foreign keys, with status fields that gate transitions between tables (e.g. a roll number can't be
generated until fee status = Approved). This is a textbook relational-integrity use case, not a document-store use
case -- PostgreSQL over MongoDB/Firebase.

2.5 Multi-Tenancy -- One Codebase, Multiple Schools

A requirement surfaced in review: the system needs to serve multiple schools from one deployment, so a code
change or bug fix applies to every school at once rather than being patched school-by-school. This is a real
architectural decision, not a config toggle, so it's made explicit here.

Recommendation: shared schema with a school_id foreign key on every tenant-scoped table (Student,
Application, Payment, Document, ApprovalStep, etc.), enforced centrally by a request-scoped NestJS
interceptor rather than repeated in every query. This is what makes "we changed the code and it changed
for everyone" true by construction -- there is only one copy of the code and one schema. School
onboarding becomes a matter of inserting a School row and its admin user, not a deployment.

2.6 Hosting & the AWS Migration Path

AWS was flagged as the target cloud in future, not necessarily day one. For a 2-person team pre-revenue, running
the MVP on AWS directly (ECS/RDS/ElastiCache) adds setup and cost overhead that isn't justified yet. The
approach below gets you to AWS without a rewrite when the time comes:

 · MVP hosting: Railway or Render for the NestJS API (managed Postgres + Redis add-ons included), Vercel or
    Netlify for the React frontend. Both are one engineer's worth of DevOps.

 · Object storage: Cloudflare R2 from day one, via the S3 SDK -- this is the one piece deliberately chosen to be
    AWS-compatible in advance.

· Migration trigger: once there's real multi-school traffic and a case for AWS's ecosystem (RDS read replicas,
   CloudFront, ECS auto-scaling), move the Postgres instance to RDS, Redis to ElastiCache, the API containers
   to ECS/Fargate, and repoint the S3 SDK from R2's endpoint to AWS S3's -- no application code changes
   required for storage.
